TODO機能 要件定義書

1. 目的・対象範囲

目的

既存の Express + TypeScript + EJS で構築されたWebアプリケーションにTODO管理機能を追加し、Vercel および Neon PostgreSQL 環境上でTODOの閲覧・登録・完了状態の更新・削除を一貫して行えるようにする。

対象範囲

画面および既存API: 既存の / および /api/db-check は変更せずそのまま残し、TODO画面は /todo に配置する。

対象API: REST APIのベースエンドポイントを /api/todo/v1/todos とし、GET、POST、PATCH、DELETE の4操作を対象とする。画面からは Fetch API を用いて非同期で通信を行う。

DB・インフラ構成: 既存の DB 接続処理および DATABASE_URL を利用する。DB は学生自身の Neon PostgreSQL、公開先は Vercel とし、Preview 環境および Production 環境で同一の Neon DB を参照する。個人情報は扱わず、架空のデータのみを使用する。

V1対象外: 認証機能、優先度、絞り込み/検索機能、タイトル更新機能は含めない。

構成の決定: ソースコードの実際のファイル配置およびクライアント側の TodoApi クラスへの分割方針は本要件定義時点では推測せず「要確認」とし、設計書にて確定させる。

2. 機能要件および受け入れ条件

REQ-01: TODO一覧取得 (GET /api/todo/v1/todos)

操作: ユーザーが /todo 画面を開いた際、画面初期化時に自動で Fetch リクエストを発行してTODO一覧を取得する。

入力: なし

結果: 登録済みのTODO一覧がレスポンスされ、画面上に一覧表示される。データが0件の場合は空配列が返却される。

エラー: サーバー・DB接続エラー（500, 503）発生時は画面上にエラー表示を行う。

受け入れ条件: データが0件の場合、レスポンスがステータス 200 かつ { "data": [] } となり、画面が正常に0件状態を描画できること。

確認方法: データベースのTODOデータを0件にした状態で /todo にアクセスし、200レスポンスおよび画面表示を確認する。

REQ-02: TODO登録 (POST /api/todo/v1/todos)

操作: フォームにタイトルを入力し、登録ボタンを押下して新TODOを作成する。

入力: リクエストボディ JSON { "title": string }（前後の空白を除いて1〜100文字）。

結果: ステータス 201 と作成されたTODOオブジェクトが返却され、画面の一覧に即座に追加される。

エラー: 前後空白除外後の文字数が0文字または101文字以上の場合、400 または 422 を返却する。

受け入れ条件: トリム後の title が1〜100文字の場合のみ正常登録（201）され、範囲外の場合はバリデーションエラーとなりDBへ保存されないこと。

確認方法: 空白のみ、1文字、100文字、101文字のタイトルを入力して送信し、レスポンスコードおよび画面・DBへの反映状況を確認する。

REQ-03: TODO完了状態の部分更新 (PATCH /api/todo/v1/todos/:id)

操作: 一覧上のチェックボックスのON/OFFを切り替え、完了状態を変更する。

入力: パスパラメータ id（1以上の整数）、リクエストボディ JSON { "is_completed": boolean }。

結果: ステータス 200 と更新後のTODOオブジェクトが返却され、画面上の表示状態が更新される。

エラー: id が1以上の整数でない場合や形式不正は 400、指定された id が存在しない場合は 404 を返却する。

受け入れ条件: 指定された id の is_completed のみが正しく更新され、画面更新後も設定された状態が維持されること。

確認方法: チェックボックスの切り替え操作を行い、通信ログと画面再読み込み後のDB保持状態を確認する。また存在しないIDへのリクエストで404が返ることを確認する。

REQ-04: TODO削除 (DELETE /api/todo/v1/todos/:id)

操作: 画面上の各TODO項目にある「削除」ボタンを押下する。

入力: パスパラメータ id（1以上の整数）。

結果: ステータス 204（本文なし）が返却され、該当TODOが画面一覧から削除される。

エラー: id が1以上の整数でない場合は 400、指定された id が存在しない場合は 404 を返却する。

受け入れ条件: 削除成功時にレスポンスボディが空の 204 No Content が返り、画面およびDBからデータが消去されること。

確認方法: 削除ボタンを押下し、ネットワークタブでレスポンスが 204 かつ本文なしであることを確認し、DBからレコードが消滅したことを確認する。

3. 共通のデータ・エラー条件

3.1 レスポンス構造の標準仕様

成功時レスポンス (200 OK / 201 Created)

{
  "data": { ... }
}


※一覧取得 (GET) の場合は data が配列 [ ... ] となり、0件時は { "data": [] } となる。
※削除成功 (204 No Content) の場合はレスポンス本文なし。

エラー時レスポンス (400 / 422 / 404 / 500 / 503)

{
  "error": {
    "code": "ERROR_CODE",
    "message": "エラーの詳細メッセージ"
  }
}


3.2 各ステータスコードの判定・判定条件

400 Bad Request: パスパラメータ id が1以上の整数でない場合、またはリクエストJSONのフォーマット自体が不正な場合。

422 Unprocessable Entity: title の前後空白を除去した結果が1〜100文字の範囲外であるなど、入力バリデーションに違反した場合。

404 Not Found: PATCH または DELETE 操作において、指定された id に一致するTODOがDB上に存在しない場合。

500 Internal Server Error: サーバー内部の予期せぬハンドリング失敗や、SQL実行エラーなどのシステム障害。

503 Service Unavailable: Neon PostgreSQL への接続失敗、タイムアウト、またはDBサービス停止時。

4. 環境別確認および構成に関する留意事項

4.1 動作確認手順

ローカルおよび Vercel Preview 環境:

設定された Neon DB（DATABASE_URL）に接続し、/todo 画面から4機能（GET/POST/PATCH/DELETE）の正常系・異常系テストを実施する。

Vercel Production 環境:

Preview と同一の Neon DB を参照してデプロイ後確認を実施する。全環境で本物の個人情報は入力せず、架空のテストデータのみを使用して動作検証を行う。

4.2 未確定箇所の扱い
